## 3. Подтверждённые дефекты

### F1. Пустое утверждение ПРОЕКТНОГО профиля обходит блокировку

**Где:** `rza_calc/core/methodology.py:253–258`, `:471–478`.

`str(None).strip()` даёт непустую строку `"None"`. Поэтому JSON `null` в `approval.approved_by`, `approval.approved_on`, `approval.object` принимается как заполненное поле. Аналогично `source: null` превращается в строку при построении `Provenance`.

Воспроизведение: взять обычный профиль, поставить ПРОЕКТНЫЙ, пометить источники подтверждёнными и присвоить трём полям утверждения `None`. `blocking_errors()` возвращает `[]`, сквозной `run()` на `ps_severnaya` выдаёт **16 результатов**. Отдельно типовой профиль с `mtz.k_ots.source = None` также не имеет блокирующих ошибок.

**Что нужно:** проверять исходный тип и непустое строковое содержимое до преобразования; добавить тесты JSON `null` и нестроковых значений. Это нарушение центрального обещания A2, а не отсутствие Qt.

### F2. Зона резервирования зависит от порядка объявления ветвей

**Где:** `rza_calc/core/context.py:232–234`.

Узел попадает в `seen` до того, как ребро-трансформатор отвергается. Когда до того же узла существует допустимый путь через параллельную линию, этот путь уже подавлен как посещённый.

Синтетическая сеть: защищаемая линия F → шины → параллельные трансформатор 10/10 кВ и обходная линия → узел b → линия → end. Меняется только порядок добавления двух параллельных ветвей. Оба варианта проходят `Network.validate()`.

| Порядок | Фактическая зона | Проверка резервирования |
|---|---|---|
| Трансформатор первым | `[]` | исчезает |
| Обходная линия первой | `['b', 'end']` | присутствует |

**Что нужно:** помечать узел посещённым после принятия ребра; закрепить независимость результата от порядка объявления и наличие разрешённого пути. Радиальный контроль из A2 проходит, но этого недостаточно для общего закрытия AUD-PROT-010.

### F3. Паспортное напряжение ВН-луча трёхобмоточного трансформатора теряется

**Где:** `rza_calc/core/protections/to.py:304–314`; создание луча — `rza_calc/core/model.py:419–429`.

Для внутреннего ВН-луча `Transformer3W` обе величины `u_hv` и `u_lv` равны одному известному паспортному напряжению. Два одинаковых совпадения считаются неоднозначностью, после чего подставляется класс узла вместо паспорта.

Сквозной пример: 32 МВА, 115/38,5/11 кВ, кратность броска 8, коэффициент 1,3. Для внутренней звезды явно задан расчётный базис 115 кВ. Проверка модели и решатель ошибок не выдают.

| Величина | Получено | По известному паспорту 115 кВ |
|---|---:|---:|
| Iном, А | 167,956… (в протоколе 168,0) | 160,653987948 |
| Условие отстройки, А | 1746,746996239 | 1670,801474664 |
| Принятая уставка после шкалы, А | 1800 | 1800 |

**Ограничение вывода:** в этом примере округление скрывает расхождение; изменение конечной принятой уставки не заявляется. Ошибка расчётного порога и пояснения подтверждена.

**Что нужно:** учитывать один уникальный кандидат либо фактическую обмотку, добавить сквозной тест для генерируемого трёхобмоточного трансформатора. Дополнительно нужен пример, где бросок определяет итоговую принятую уставку: существующий `test_to_inrush_basis.py:128` сравнивает Iном, а в его сети при обоих основаниях итог 800 А, поскольку определяет внешнее КЗ.

### F4. Старый протокол продолжает читать живые расшифровки источников

**Где:** `rza_calc/cli.py:121`.

Коэффициенты берутся из снимка, а таблица расшифровок — из `meth.references()`. После `run()` изменение `methodology.data['references']['ПУЭ']` меняет результат `cmd_methodology(old_result)`; новый текст появляется в старом протоколе.

**Что нужно:** заморозить полные расшифровки источников вместе со снимком и печатать их из него. Проверять неизменность всего соответствующего раздела протокола, а не только одного числового коэффициента.

### F5. Файл профиля может сам разрешить неизвестное основание Iном

**Где:** `rza_calc/core/methodology.py:228–235`; использование — `rza_calc/core/protections/to.py:302`.

`to.i_nom_basis = {value: 'garbage', options: ['garbage'], ...}` проходит `blocking_errors()`: список допустимых вариантов берётся из того же редактируемого JSON. Расчётная ветка различает только `stage_average`, а прочие строки фактически трактует как `nameplate`.

**Что нужно:** проверять реализованные варианты независимо от пользовательского `options`. Неизвестное решение должно блокироваться, а не молча попадать в другую ветку.

### F6. OPEN-14 закрыт не полностью: неизвестное присоединение даёт код 1

**Где:** `rza_calc/cli.py:294`, обработка команды `:336–359`.

Команда `python -m rza_calc rza_calc/examples/ps_severnaya.json feeder __does_not_exist__` возвращает **1**, поскольку `_find()` вызывает `SystemExit(строка)`. Это ошибка запроса, а не непройденная защита; по контракту A2 ожидается **2**. Аналогичный путь используется `explain`.

**Что нужно:** переводить неизвестный идентификатор в штатную ошибку входа и добавить проверки реальных кодов процесса для `feeder`/`explain`.

## 4. Отдельно: не выполнен критерий долговременного воспроизведения

ТЗ A2 требует воспроизвести старый расчёт по **сохранённому паспорту** после изменения внешней методики. В отчёте Max этот критерий отмечен выполненным.

Фактически `MethodologySnapshot` хранится в оперативном `CalculationCase`. В приложении нет пути сохранения/загрузки этого снимка или восстановления методики для повторного расчёта. `save_project()` (`rza_calc/io/project.py:2114`, формирование payload `:2158–2178`) не записывает паспорт расчёта. Сериализация снимка `as_dict()` используется только тестом.

Тест с названием `test_snapshot_survives_a_later_edit_of_the_profile_file` изменяет словарь в памяти; он не редактирует файл, не сохраняет/загружает паспорт и не повторяет расчёт по восстановленному снимку.

Это не отрицание выполненной части: обычные числовые значения в снимке действительно отделены от дальнейших изменений исходного словаря. Но долговременное хранение и повторяемость этим не доказаны и не реализованы. Нужно либо реализовать отдельное сохранение/восстановление паспорта с round-trip проверкой, либо честно снять отметку выполнения и отдельно согласовать оставшуюся работу.

## 5. Неточность отчётности

В полученном `status.json`: `passed=575`, `total=606`, `failed=32`. Сумма passed + failed равна 607. Примечание «31 Qt + 1 sandbox» также даёт 32, а не разность 606−575=31. Это отдельная несогласованность старого мини-раннера; фактический Windows pytest **783/783** получен независимо.
