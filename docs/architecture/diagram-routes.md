# Графические трассы соединений

## Назначение

`DiagramRoute` хранит только способ изображения соединения на странице:
привязки концов, ортогональные точки и версию алгоритма маршрутизации.
Электрическая связность хранится в `ElectricalModel` как оборудование, порты,
узлы и `Connection`.

Из этого следуют обязательные правила:

- перемещение символа или точки маршрута не меняет электрический узел;
- графическое пересечение трасс не создаёт электрическую связь;
- физическая длина не вычисляется по координатам;
- низкоуровневое удаление только `DiagramRoute` не изменяет электрическую
  модель, поэтому пользовательское удаление соединения выполняется отдельной
  составной командой контроллера;
- изменение электрического подключения выполняется доменной транзакцией, после
  которой графическая трасса лишь перепривязывается.

## Два вида трасс

### Графическое соединение одного узла

`DiagramRouteKind.NODE_CONNECTION` показывает, что два графических места
принадлежат одному уже существующему `ElectricalNodeId`. Это может быть линия
от порта аппарата к шине, соединение точки узла с шиной или будущее
межсхемное представление.

У такой трассы:

- `electrical_node_id` обязателен;
- `equipment_id` отсутствует;
- оба `RouteEndpointAnchor.electrical_node_id` совпадают с ID трассы;
- `branch_port_id` отсутствует, потому что отдельной физической ветви нет.

Одна графическая полилиния не превращается в электрическую ветвь и не получает
сопротивление.

### Трасса физической ветви оборудования

`DiagramRouteKind.EQUIPMENT_BRANCH` изображает самостоятельное двухпортовое
оборудование: ВЛ, КЛ, шинопровод, реклоузер или другой ветвевой объект.

У такой трассы:

- `equipment_id` обязателен;
- `electrical_node_id` самой трассы отсутствует;
- начала и конец принадлежат двум разным узлам;
- каждый конец хранит собственный `branch_port_id` физической ветви;
- два `branch_port_id` различны и принадлежат указанному оборудованию;
- подключение каждого порта в `ElectricalModel` обязано вести в узел своего
  конца.

Это не позволяет потерять соответствие «порт начала — узел начала» и «порт
конца — узел конца» после сохранения, загрузки или переподключения.

## Привязка конца

`RouteEndpointAnchor` содержит:

| Поле | Смысл |
|---|---|
| `kind` | вид графической цели |
| `representation_id` | постоянный ID символа или представления узла |
| `electrical_node_id` | электрический узел этого конца |
| `branch_port_id` | собственный порт изображаемой физической ветви |
| `target_port_id` | порт целевого аппарата, если конец привязан к его символу |
| `anchor_key` | стабильное имя графической точки символа |

Поддержаны четыре вида цели:

- `equipment_port` — порт аппарата; `target_port_id` обязателен;
- `electrical_node` — представление электрического узла;
- `bus` — место на графическом изображении шины;
- `cross_diagram_port` — подготовленная привязка к представлению того же узла
  на другой странице.

`branch_port_id` и `target_port_id` намеренно разделены. Например, конец ВЛ,
привязанный к выключателю, хранит порт самой ВЛ в `branch_port_id`, а порт
выключателя — в `target_port_id`. При подключении обычного порта аппарата к
шине отдельной физической ветви нет, поэтому `branch_port_id=null`; у шины нет
выдуманного порта, поэтому её конец содержит `target_port_id=null` и тот же
`ElectricalNodeId`.

## Точки маршрута

`RouteWaypoint` имеет постоянный `RouteWaypointId`, координаты, источник и
признак закрепления:

- `source=automatic` — точку построил маршрутизатор;
- `source=user` — точку создал или зафиксировал пользователь;
- `pinned=true` допустимо только для пользовательской точки.

Сохраняется вся ортогональная полилиния, включая конечные точки. Инварианты:

- не менее двух точек;
- ID точек не повторяются;
- соседние точки не совпадают;
- каждый сегмент горизонтальный либо вертикальный.

Автоматическая перестройка вправе заменять автоматические точки, но обязана
сохранять закреплённые пользовательские точки либо явно сообщить, что маршрут
невозможен. `routing_algorithm_version` фиксирует версию алгоритма, создавшего
геометрию.

## Редактирование сохранённой трассы

Для уже сохранённой трассы контекстное действие «Добавить точку маршрута»
находит ближайший сегмент, добавляет в указанном месте новую точку
`source=user, pinned=true` и локально восстанавливает строгую ортогональность.
При выделении трассы закреплённые точки получают отдельные маркеры: их можно
перетаскивать, а через контекстное меню точки — удалять.

У достаточно длинных внутренних сегментов выбранной трассы появляются
маркеры перемещения. Горизонтальный сегмент перемещается только по вертикали,
вертикальный — только по горизонтали. Два его угла становятся закреплёнными
пользовательскими точками; существующие ID точек сохраняются там, где это
однозначно. Первый и последний сегменты не перемещаются этим жестом, потому
что они привязаны к электрическим окончаниям; для физической ветви их меняют
отдельными маркерами переподключения портов.

Добавление точки, перенос точки, удаление точки и перенос внутреннего сегмента
вызывают одну команду `reroute_diagram_route()`. Она изменяет только набор
`RouteWaypoint` и графическую revision, не меняет электрическую revision,
топологический отпечаток или физическую длину и создаёт один шаг undo.

## Операции `DiagramDocument`

Графическая модель неизменяема по значению. Публичные операции над данными
возвращают новый документ и увеличивают `revision`:

- `add_route()` — добавить трассу;
- `remove_route()` — удалить трассу;
- `rerouted_route()` — атомарно заменить точки;
- `reanchor_route()` — атомарно заменить обе привязки;
- `remove_representation(cascade_routes=True)` — удалить представление вместе
  с зависимыми трассами.

Без явного `cascade_routes=True` удаление используемого представления
запрещается. Контроллер не должен изменять private mapping документа.

При копировании группы создаются новые ID трасс и точек. ID представлений,
оборудования, портов и узлов переадресуются только если соответствующая
сущность действительно скопирована; внешнюю электрическую связь нельзя
молчаливо дублировать.

## Пользовательское удаление трассы

Контекстное действие «Удалить соединение или линию» вызывает не
`DiagramDocument.remove_route()` напрямую, а атомарную команду
`ProjectEditorController.delete_diagram_route()`:

- для `NODE_CONNECTION` удаляется трасса и адресованные ею `Connection`;
  электрический узел удаляется только когда после этого у него нет
  подключений, представлений и других трасс;
- для физической `EQUIPMENT_BRANCH` удаляется соответствующий `LineSection`;
  если он был единственным, удаляется вся `LogicalLine`, иначе применяется
  доменная операция удаления участка с сохранением оставшихся частей;
- конечные узлы физической линии не удаляются автоматически;
- зависимые графические ссылки и каталожная привязка удаляемого участка
  очищаются в том же `ProjectDraft`.

Один undo восстанавливает электрические записи, графическую трассу и прежние
ID. Это пользовательское действие не меняет принцип источника истины:
решение о том, что именно удалить, принимает контроллер по явному виду трассы,
а не сама графическая геометрия.

## Проверка ссылок

`DiagramDocument.validate_targets()` сверяет трассы с `ElectricalModel`:

- оборудование и узлы существуют;
- целевой порт принадлежит символу целевого оборудования и подключён к
  указанному узлу;
- порт физической ветви принадлежит самой ветви и подключён к узлу конца;
- два электрических узла `equipment_branch` совпадают с узлами оборудования;
- привязка к шине или узлу ссылается на графическое представление того же
  электрического узла;
- страница трассы совпадает со страницами её привязок;
- ID документа, страниц, представлений, трасс и точек уникальны.

Строгий кодек diagram v2 дополнительно отвергает неизвестные поля, неверные
JSON-типы, `NaN`, `Infinity`, неортогональные и нулевые сегменты.

## Миграция старых `route_points`

Diagram v1 хранил точки непосредственно в
`GraphicalRepresentation.route_points` без отдельного ID трассы, без ID точек
и без однозначных привязок концов.

Миграция v6→v7 преобразует такую геометрию только при доказуемом смысле:

- представление электрического узла становится `node_connection`;
- двухпортовый `LineSection` с двумя однозначными подключениями становится
  `equipment_branch`;
- исходная полилиния обязана быть строгой ортогональной трассой.

Новые ID трассы и точек детерминированы и проверяются на коллизии со всеми ID
проекта. Старые точки становятся пользовательскими и закреплёнными, поэтому
миграция не меняет увиденную пользователем форму.

Если смысл или концы определить нельзя, миграция не угадывает. Исходные
`route_points` сохраняются, а в `extensions` представления добавляется признак
`rza_calc.stage4_migration_review`. Такой объект должен быть явно проверен
пользователем; неподтверждённая электрическая ветвь не допускается к расчёту.

## Граница производительности

Маршрутизатор работает по локальному набору препятствий и перестраивает только
изменённую трассу либо зависимые трассы. Перемещение одной точки не должно
пересобирать `ElectricalModel`, всю активную топологию или все маршруты проекта.
Производительность оценивается измерениями на модели не менее 1000 объектов,
1500 соединений, 200 точек ответвления и 50 реклоузеров.
