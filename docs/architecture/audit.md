## Резюме

Проект не следует переписывать с нуля. В нём уже есть полезное расчётное ядро, режимы сети, версионированный JSON, набор регрессионных тестов, настольный интерфейс и качественная автоматическая SVG-трассировка обзорной схемы.

Однако текущая программа — это просмотрщик и расчётчик заранее описанного JSON-графа, а не редактор цифровой модели сети. Главный инвариант целевой системы пока не выполнен: пользователь не рисует схему, из которой автоматически возникает электрический граф. Наоборот, узлы и ветви вручную задаются в JSON через `node_from`/`node_to`, после чего GUI реконструирует картинку из этого расчётного графа.

Самый безопасный путь — сохранить существующий расчётный код за адаптером, в Этапе 1 ввести каноническую Domain Model с портами и соединениями, затем постепенно перевести topology/UI/serialization на неё. До появления адаптера и миграционных тестов удалять или массово переписывать существующее ядро нельзя.

## Что уже работает

### Расчётная сеть и режимы

- Узлы и ветви образуют полноценный неориентированный multigraph; поддерживаются параллельные ветви и кольца.
- Есть генераторы, внешний источник, линии, двух- и трёхобмоточные трансформаторы, tie-ветви и нагрузки.
- Режимы являются отдельными объектами и хранят состояния ветвей/синтезированных выключателей.
- Активная топология умеет учитывать OPEN/CLOSED, находить компоненты, источники и запитанные узлы.
- Для выключателя создана расширенная терминальная топология, поэтому напряжение по разные стороны открытого аппарата различается корректно.
- Есть проверки дубликатов внутри основных коллекций, повреждённых ссылок, параметров ТТ, режимов и части оборудования.

### Расчётное ядро

- Трёхфазное КЗ рассчитывается через матрицу узловых проводимостей.
- Двухфазное КЗ выводится через методический коэффициент от трёхфазного.
- Поддержаны параллельные пути и распределение тока по ветвям с явной ошибкой для неоднозначного идеального нулевого контура.
- Расчётные результаты и протокол шагов отделены от GUI.
- Неверные или неполные данные во многих случаях блокируют расчёт вместо выдачи ложного результата.

### Project format

- Формат имеет явный `format_version`.
- Более новый неизвестный формат отклоняется.
- Неизвестные поля отклоняются, а не молча игнорируются.
- Есть миграция v1 → v2 и round-trip тесты.
- Служебные лучи трёхобмоточного трансформатора не сериализуются как независимое физическое оборудование.

### GUI и визуализация

- GUI действительно запускается как настольное приложение.
- Есть дерево, обзорная схема, inspector, нижние вкладки, выбор режимов и генераторов.
- Колесо мыши масштабирует, свободное поле панорамируется, двойной щелчок приближает объект.
- ViewBox и выделение сохраняются в памяти при перестроении SVG.
- Объекты SVG кликабельны; выключатели переключаются транзакционно с пересчётом и откатом при ошибке.
- Ортогональная маршрутизация различает параллельные линии, строит мостики пересечений и избегает блоков объектов.
- Штатный SVG-аудит на демонстрационной сети не нашёл наложенных трасс, висящих концов, немаркированных пересечений, пересечений блоков и конфликтов подписей.

### Тесты

- При `PYTHONUTF8=1` штатный `python tests/run_tests.py` проходит 115/115 тестов.
- Покрыты расчётные формулы, режимы, параллельные пути, электрические состояния, сериализация, миграция, ViewModel и геометрия SVG.
- GUI smoke-test `python -m rza_calc.gui --smoke-test` завершился с кодом 0.
- CLI `check` и `sc` выполняются на демонстрационном проекте.

## Что реализовано частично

### Domain Model

`ProjectStructure` отделён от `Network`, что является хорошим направлением, но пока это только физико-навигационная надстройка. Оборудование не владеет электрическими портами и не формирует расчётную сеть. `CalculationRef` направлен от физического аппарата к уже созданной вручную расчётной ветви, поэтому источником истины фактически остаётся `core.Network`.

### Уникальные ID

ID используются вместо имён в большинстве расчётных ссылок. Но ID вводятся вручную, генератора ID нет, типизированных ID нет, а глобальная уникальность между всеми категориями не обеспечивается. Синтезированные выключатели получают предсказуемый ID `SW:<branch>:<end>`, но не являются сохранёнными domain-объектами.

### Типы оборудования

Есть несколько расчётных типов и несколько физических `EquipmentKind`, но набор неполон. Один `Branch` одновременно несёт параметры проводника, выключателя, ТТ, терминала и защит. Разъединители, заземляющие разъединители, предохранители, реакторы, ТН, двигатели и другие требуемые аппараты не имеют самостоятельной электрической модели.

### Валидация

Проверки существенны для существующего расчёта, но нет непрерывной validation model, severity, ссылок на объект/поле и Problems API. Не проверяются электрические порты, совместимость соединений, наследование напряжения и межсхемные связи, потому что этих сущностей нет.

### View state

Масштаб, панорамирование и выбор сохраняются только в памяти `SvgDiagramView`. В проект они не записываются. Нет отдельных viewport для нескольких схем.

### Project format v2

Версионирование и строгая загрузка реализованы, но v2 не хранит Diagram Model, connections/ports, подсхемы, маршруты, viewport, каталоги, настройки отображения или Result Layer. Миграция v1 создаёт пустой физический слой и не даёт пользователю работоспособный domain-проект.

### Справочники

Есть небольшой `cables.json` и профиль методики, но это не `SystemCatalog`/`UserCatalog`. Нет происхождения записи, версии, производителя, пользовательского override и сохранения экземпляра в каталог.

### Тестовая сеть

Демонстрационный JSON содержит значительную сеть ГТЭС → ПС → КТП и режимы. Она полезна как расчётный regression fixture, но не проверяет построение пользователем, порты, соединения, подсхемы и повторное открытие Diagram Model.

## Что реализовано неправильно

### 1. Направление формирования модели обратное целевому

Сейчас пользователь или скрипт сначала вручную задаёт `nodes` и `branches` с `node_from`/`node_to`. GUI только рисует этот граф. Целевой принцип требует обратного потока: действия в редакторе создают/изменяют equipment, ports и connections, а topology/calculation graph строится автоматически.

### 2. Визуальная группировка зависит от имён и шаблонов ID

`SvgSchemeBuilder._facility_from_text()` ищет `КТП-<номер>`, `ПС <имя>`, `ГТЭС` и `ГТГ`; `_discover()` также распознаёт `G<номер>_bus`, `AT...` и слова в названиях трансформаторов. Переименование способно изменить визуальное представление. Это допустимо только как временный legacy-import fallback, но не как архитектура редактора.

### 3. Нет электрических Port и Connection

`FacilityPort` в SVG-builder — лишь геометрическая точка маршрута и не является электрическим портом. Электрические связи хранятся непосредственно в полях ветви. Поэтому нельзя программно обеспечить инварианты допустимых соединений, принадлежности порта оборудованию, количества подключений и классов напряжения.

### 4. Коммутационные аппараты синтезируются из ветвей

Выключатель не является самостоятельным domain equipment: количество выключателей выводится из класса ветви, а состояние хранится под синтезированным ID. Это не позволяет корректно моделировать произвольную последовательность QS/QF/CT/VT, несколько аппаратов на присоединении и независимые характеристики каждого аппарата.

### 5. Существуют две конкурирующие реализации топологии

`Network.adjacency()/energized_nodes()/orient()` и `core.electrical.ActiveTopology` строят разные представления. Вторая специально исключает общий `GRID` из физической связности островов, первая использует `GRID` в обходах. Это создаёт риск расхождения состояния SVG, зон защит, ориентации и расчётной матрицы в сложных сетях с несколькими независимыми источниками.

### 6. Diagram Model отсутствует

Координаты вычисляются автоматически при каждом построении. Нет diagram element ID, пользовательских координат, symbol reference, z-order, waypoint, page/subscheme, boundary port, маршрутов или viewport в проекте. Перемещать оборудование невозможно.

### 7. Выявлено расхождение SVG с расчётной моделью

Штатный `audit_svg.py` показал, что на трёх уровнях (`ПС Восток` 110 и 35 кВ, `ПС Северная` 110 кВ) нарисованы две секции шин при одной секции в модели. Геометрия трасс качественная, но семантика части символов уже расходится с данными.

### 8. Поставляемые примеры и документация расходятся

README сообщает 85 тестов, инструкция запуска — 77, фактически проходит 115. README описывает v2 и физическую структуру, но оба примера остаются v1 и мигрируют в пустой `ProjectStructure`.

### 9. Стресс-инструмент устарел

`audit_svg.py --stress` не создаёт валидный проект: добавляемая ветвь ссылается на отсутствующий узел `VF1_end`. Инструмент нельзя считать рабочим performance/geometry test до исправления fixture.

## Что можно сохранить

- Python + PySide6 как текущую desktop-платформу: причин менять стек на Этапе 1 нет.
- `core` как legacy calculation engine за явным адаптером, не расширяя сейчас РЗА.
- Формат строгой загрузки, принцип версий и последовательных миграций.
- Идею отдельного `ProjectStructure`, но не текущую модель ссылок как конечную архитектуру.
- Расчётные dataclass оборудования как DTO целевого calculation adapter.
- `Mode` как концепцию operating state, после переноса состояний на реальные equipment ID.
- `ElectricalMap` и отдельный Result Model как интерфейс для overlay, после объединения topology engine.
- SVG symbol/rendering слой и большую часть ортогональной маршрутизации.
- ViewModel как границу без PySide6, разделив чтение и команды изменения.
- CLI и существующие 115 regression tests.
- Демонстрационную сеть как legacy calculation fixture и источник данных для будущей канонической эталонной сети.

## Что необходимо изменить

1. Ввести канонические `Project`, `Equipment`, `ElectricalNode`, `Port`, `Connection`, `OperatingState` и типизированные стабильные ID.
2. Сделать Domain Model + connectivity единственным источником истины.
3. Убрать из domain зависимость на расчётные `node/branch/load`; зависимость должна идти через calculation adapter в противоположном направлении.
4. Моделировать QF/QS/CT/VT и другие аппараты как самостоятельные equipment с собственными портами.
5. Объединить построение активной топологии в один UI-независимый модуль.
6. Добавить Voltage Class/value object и распространение напряжения по connectivity graph с трансформаторными границами.
7. Создать отдельную Diagram Model; SVG должен читать её, а не угадывать объект по имени.
8. Расширить project schema до следующей версии только после утверждения Domain Model; добавить последовательную миграцию.
9. Перевести поставляемые примеры в новый формат и сохранить legacy v1 fixtures отдельно.
10. Разделить validation issues по коду, severity, object ID и field/port ID.
11. Ввести command boundary для будущего undo/redo и транзакционных изменений.
12. Настроить воспроизводимое окружение разработки (`pyproject.toml` или эквивалент, dev dependencies, type checker/linter — после согласования конкретных инструментов).

## Что необходимо удалить

Удаление выполнять не на Этапе 0 и только после покрытия миграционными тестами:

- неиспользуемый QGraphicsView-класс `DiagramView` и связанные импорты из `main_window.py`; активный экран использует `SvgDiagramView`;
- name/ID heuristics в `_facility_from_text()` и `_discover()` после перевода всех поддерживаемых проектов на явную Diagram/Domain Model; до этого оставить только в legacy importer;
- автоматическое `_enable_switching()`, которое мутирует загруженную модель на основании наличия ТТ/времени выключателя, после явной миграции аппаратов;
- устаревшие счётчики тестов и противоречивые утверждения документации;
- сломанный или неактуальный stress fixture после замены воспроизводимым тестом.

Расчётное ядро, РЗА-модули и старые loader paths удалять нельзя: их следует заморозить и использовать для regression comparison до появления проверенного адаптера.

## Риски архитектуры

### Критические

- Ручной расчётный граф вместо графа, порождённого редактором.
- Отсутствие port/connection model.
- Конкурирующие topology implementations.
- Смешивание нескольких физических аппаратов в одной `Branch`.
- Отсутствие Diagram Model и подсхем.
- Dirty worktree: в ветке `main` 18 изменённых и 13 untracked путей; среди untracked целиком находятся `domain/`, `gui/`, `core/electrical.py` и новые тесты. Единственный commit — baseline 0.2. Потеря или неосторожный reset уничтожит значительную часть текущей работы.

### Высокие

- Имена участвуют в восстановлении визуальной структуры.
- Примеры v1 не проверяют заявленную v2-архитектуру.
- Миграция v1 → v2 создаёт пустой физический слой.
- Mutable dataclass/dict state меняется напрямую; нет централизованных команд и инвариантов транзакции.
- `Literal` создаёт видимость строгой типизации, но без type checker и runtime validation недопустимые значения могут попасть в модель.
- В проекте нет механизма безопасного удаления каскадных ссылок, clipboard re-ID и undo/redo.

## Риски производительности

- `ShortCircuitSolver` строит и обращает плотную матрицу NumPy отдельно для каждого режима. Время порядка O(V³), память O(V²); тысячи узлов в таком виде непрактичны.
- Каждый переключатель вызывает полный расчёт всех режимов и полную регенерацию HTML/SVG. На текущем примере только расчёт занимает около секунды.
- `SvgDiagramView.refresh()` загружает заново документ порядка 184 тысяч символов; сохранение view state не устраняет стоимость полной перезагрузки DOM.
- SVG-builder содержит многократные полные обходы сети, попарные проверки сегментов/подписей и рекурсивный layout без кэша.
- Нет incremental topology/validation, spatial index, viewport culling или виртуализации.
- `main_window.py` (1251 строка) и `svg_scheme.py` (1692 строки) уже велики; дальнейшее добавление редактора внутрь этих файлов быстро создаст god-components.
- Существующий stress fixture не работает и не даёт достоверной границы масштабирования.

До Этапа 9 оптимизировать solver преждевременно, но уже сейчас новые модели и API не должны требовать полного UI/recalculation update на каждое движение мыши.

## Риски расчётного ядра

- Реализована в основном прямая последовательность: `Iк(2)` получается коэффициентом от `Iк(3)`, отдельные сети обратной и нулевой последовательности отсутствуют.
- Нет 1Ф и 2Ф-земля КЗ, явных neutral/grounding equipment и трансформаторных соединений для нулевой последовательности.
- Поля линий `r0/x0` по смыслу используются как сопротивления существующего расчёта прямой последовательности, хотя обозначения в целевой модели должны недвусмысленно разделять `R1/X1/R2/X2/R0/X0`.
- Общий служебный `GRID`, отрицательные лучевые сопротивления и две топологии требуют отдельной верификации на сложных многoисточниковых островах.
- Методика по умолчанию и кабельные данные прямо помечены как заглушки; результаты нельзя применять на реальном объекте.
- Расчётные формулы покрыты тестами, но нет зафиксированного набора нормативных источников и верифицированных эталонных кейсов для будущего ТКЗ.
- Расчёт уставок РЗА уже присутствует, но по текущему roadmap его развитие следует остановить. Сохранить только как legacy regression subsystem.

## Рекомендуемая архитектура

### 1. Domain Model — каноническая физическая сеть

```text
Project
├── equipment: EquipmentInstance[id]
│   └── ports: Port[id]
├── electrical_nodes: ElectricalNode[id]
├── connections: Connection[id]
├── operating_states: OperatingState[id]
├── diagrams: Diagram[id]
├── catalogs
└── calculation_results (отдельно от исходной модели)
```

`EquipmentInstance` хранит тип, имя, паспортные данные и стабильные `port_id`. `Connection` создаётся действием редактора и соединяет только допустимые электрические порты/узлы. Пользователь не редактирует `node_from/node_to`: topology compiler получает их из connections.

Тип оборудования лучше хранить расширяемым строковым `type_id` со схемой параметров/портов, а не закрытым `Literal`, который потребует правки фундаментальных классов для каждого нового типа. Для встроенных типов остаются проверяемые определения, пользовательское оборудование получает отдельный namespace.

### 2. Connectivity/Topology Engine — один модуль

Topology engine получает Domain Model и OperatingState и возвращает:

- канонические электрические узлы и активные ветви;
- connected components/islands;
- source reachability;
- OPEN/CLOSED connectivity;
- voltage propagation/conflicts;
- пути и соседей;
- diagnostics с object/port IDs.

И GUI, и calculation adapter используют один и тот же snapshot. Отдельные реализации `Network` и `ActiveTopology` не должны независимо отвечать на одинаковый вопрос.

### 3. Diagram Model — только представление

`Diagram`, `DiagramElement`, `DiagramPortAnchor`, `ConnectionRoute`, `Waypoint`, `Viewport`. Diagram element ссылается на domain ID, но координаты не входят в электрические расчёты. Несколько диаграмм могут показывать одну физическую модель.

SVG-symbol renderer остаётся отдельным слоем и читает Diagram Model. Автоматический layout можно оставить как команду для импортированных legacy-проектов, но его результат должен сохраняться и затем редактироваться пользователем.

### 4. Подсхемы

Подсхема — diagram/page hierarchy, а не отдельный network. `BoundaryPort`/`SubschemePort` хранит ссылку на тот же domain port/electrical node. Переход между страницами не создаёт сопротивление и не разрывает topology snapshot.

### 5. Calculation Adapter

Отдельный адаптер преобразует проверенный topology snapshot в DTO существующего `core.Network`. Это позволит:

- сохранить текущие расчёты и тесты;
- сравнивать legacy и новый путь;
- не тащить SVG/coordinates в solver;
- позже заменить solver без изменения editor/domain.

### 6. Result Model

Результаты immutable и привязаны к `calculation_run_id`, topology revision и domain IDs. Overlay читает Result Model, но не изменяет equipment properties.

### 7. Application/Command layer

Все изменения выполняются командами (`AddEquipment`, `ConnectPorts`, `Disconnect`, `ChangeProperty`, `SetSwitchState`). Команда проверяет инварианты, обновляет revision и публикует минимальный change set. В дальнейшем это естественная база для undo/redo, autosave и incremental validation.

## План миграции без потери существующей работы

1. До начала Этапа 1 сохранить текущий dirty worktree отдельным commit/веткой или архивной копией. Ничего не reset/checkout.
2. Зафиксировать 115 текущих тестов как legacy regression suite и добавить единый UTF-8 entry point.
3. Переименовывать существующий `core.Network` пока не нужно; считать его legacy calculation DTO и запретить новые UI-зависимости.
4. Добавить новую каноническую модель рядом, но не как вторую долгоживущую архитектуру: сразу определить односторонний adapter `Domain → Calculation` и срок удаления прямого JSON `nodes/branches` из пользовательского формата.
5. Написать legacy importer v1/v2. Он может детерминированно создать equipment/ports/connections из `node_from/node_to`, но name heuristics использовать только для диаграмм и выводить предупреждения о неоднозначности.
6. На малой эталонной сети сравнивать topology snapshot и результаты существующего solver до/после адаптации.
7. Перевести `gtes_sever` в новый формат через мигратор; старый файл сохранить отдельным fixture.
8. После успешного round-trip переключить GUI viewer на новый snapshot и Diagram Model.
9. Только затем удалить `CalculationRef`-центричную связь, name heuristics из production path и неиспользуемый QGraphics renderer.

## Конкретный план Этапа 1

Этап 1 должен нормализовать только Domain Model, stable IDs, ports, connections и базовую сериализацию. Topology algorithms, полноценный editor, подсхемы и новые расчёты не реализовывать.

### 1. Контракты и инварианты

- Зафиксировать ID types/factory и глобальную политику уникальности.
- Ввести `VoltageClass`/`VoltageSpec` с требуемыми начальными уровнями и расширяемой регистрацией.

- Определить `ElectricalNode` и `Connection` так, чтобы связи создавались только через порты.

### 3. Operating state

- Не синтезировать выключатель из branch class.
- Пока не реализовывать сложные режимные расчёты; обеспечить только сохранение и domain validation OPEN/CLOSED.

### 4. Project schema v3

- Описать sections `equipment`, `ports`, `electrical_nodes`, `connections`, `operating_states`.
- Не добавлять Diagram Model раньше согласования его контракта, но зарезервировать независимую секцию без координат в domain.
- Реализовать строгую загрузку, сохранение и последовательную миграцию v1/v2 → v3.
- Не менять исходный файл при открытии; миграция сохраняется только по явной команде.

### 5. Legacy calculation adapter

- Построить read-only `DomainToLegacyNetworkAdapter` для малого набора типов.

## Итоговая оценка

Текущий код — сильный прототип расчётного ядра и обзорного интерфейса, но слабая основа именно для редактируемой цифровой модели. Главная ценность проекта находится в regression tests, расчётных DTO/solver, строгом JSON-loader и SVG routing. Главный долг — отсутствие канонической портовой Domain Model и Diagram Model.

Рекомендуется перейти к Этапу 1 только после подтверждения пользователем и предварительной фиксации dirty worktree. До подтверждения никаких изменений архитектуры или расчётов выполнять не следует.
