# Формат проекта

## Версии и источник истины

Текущий канонический сохраняемый формат проекта — **v7**. Загрузчик читает
версии v1–v7, а `save_project()` всегда пишет v7. Источником электрической
истины остаётся `ElectricalModel`; графическая секция не определяет связность и
не задаёт физическую длину линии.

История формата:

- v1/v2 — прежний `core.Network` и переходная физическая структура;
- v3 — канонический `ElectricalModel`;
- v4 — логические линии, электрические ветви и пользовательский каталог;
- v5 — раздельная эксплуатационная доступность оборудования;
- v6 — конструктивные участки, страницы, представления, снимки каталога и
  журнал миграций;
- v7 — отдельные сохраняемые ортогональные трассы diagram v2, постоянные ID
  точек маршрута, явные привязки концов, принадлежность фидеру и признаки
  подтверждённости физических данных линии.

`core.Network` не сериализуется параллельно с объектной моделью в v3–v7. Он
строится односторонним адаптером только как совместимое производное
представление.

## Верхний уровень v7

Набор полей верхнего уровня проверяется строго: неизвестные и пропущенные поля
отвергаются.

```json
{
  "format_version": 7,
  "project": {"name": "..."},
  "methodology": {"file": "..."},
  "structure": {
    "facilities": [],
    "voltage_levels": [],
    "bus_sections": [],
    "bays": [],
    "equipment": [],
    "placements": []
  },
  "electrical_model": {},
  "diagram": {
    "format_version": 2,
    "id": "diagram_main",
    "name": "Однолинейная схема",
    "revision": 0,
    "pages": [],
    "representations": [],
    "routes": [],
    "extensions": {}
  },
  "catalogs": {},
  "catalog_snapshots": {},
  "migration_journal": []
}
```

`methodology` остаётся опциональной ссылкой либо встроенным объектом.
`project.name` обязано быть непустой строкой и совпадать с
`electrical_model.name`. Переходная `structure` используется для совместимой
навигации, но не определяет электрические соединения.

## Электрическая модель

Секция `electrical_model` хранит оборудование, его порты, электрические узлы,
явные подключения портов, режимы, логические линии и физические ветви. Кодек
проверяет ссылки и инварианты после полной сборки модели; объект с портом без
владельца, ветвь с удалённым узлом или дублирующий ID загрузить нельзя.

### Линии в v7

`logical_lines[]` содержит пользовательскую идентичность линии. Поле
`feeder_id` может быть `null`; несколько логических линий вправе относиться к
одному фидеру, например две части маршрута по разные стороны вставленного
реклоузера. `voltage_class_id` также может быть `null`, пока класс напряжения
честно неизвестен.

`line_sections[]` хранит физическую ветвь между двумя электрическими узлами и
упорядоченные `construction_segments`. Для каждого конструктивного участка
сохраняются:

- постоянный `id`;
- `length_mm`, равный положительному целому числу либо `null`;
- собственные параметры и расширения;
- `length_confirmation`: `confirmed` или `unconfirmed`;
- `impedance_confirmation`: `confirmed` или `unconfirmed`.

`null` не заменяется нулём и не выводится из координат холста. Геометрическая
длина трассы не является физической длиной. Неподтверждённые данные допустимы
для целостного редактируемого проекта, но являются блокером расчёта.

## Графическая модель diagram v2

`DiagramDocument` хранит страницы, представления и отдельную коллекцию
`routes[]`. Представление ссылается ровно на оборудование либо электрический
узел. Один и тот же `ElectricalNodeId` может иметь несколько представлений на
разных страницах.

Каждая трасса содержит:

```json
{
  "id": "route_...",
  "page_id": "page_...",
  "kind": "node_connection",
  "equipment_id": null,
  "electrical_node_id": "node_...",
  "start_anchor": {
    "kind": "equipment_port",
    "representation_id": "representation_...",
    "electrical_node_id": "node_...",
    "branch_port_id": null,
    "target_port_id": "port_...",
    "anchor_key": "right"
  },
  "end_anchor": {
    "kind": "bus",
    "representation_id": "representation_...",
    "electrical_node_id": "node_...",
    "branch_port_id": null,
    "target_port_id": null,
    "anchor_key": "bus"
  },
  "waypoints": [
    {"id": "waypoint_1", "x": 100.0, "y": 80.0,
     "source": "user", "pinned": true},
    {"id": "waypoint_2", "x": 220.0, "y": 80.0,
     "source": "automatic", "pinned": false}
  ],
  "routing_algorithm_version": 1,
  "extensions": {}
}
```

Допустимы два разных смысла трассы:

- `node_connection` — изображение одного уже существующего электрического
  узла; оба конца обязаны ссылаться на один `ElectricalNodeId`;
- `equipment_branch` — изображение физической ветви оборудования между двумя
  различными узлами; `branch_port_id` каждого конца хранит собственный порт
  ветви, а `target_port_id` при привязке к символу — отдельный порт целевого
  аппарата.

Для привязки к шине или графическому представлению узла искусственный порт
шины не создаётся: достаточно `electrical_node_id`, а `target_port_id` равен
`null`. Поддержаны виды привязки `equipment_port`, `electrical_node`, `bus` и
`cross_diagram_port`.

Каждая сохраняемая точка трассы имеет собственный `RouteWaypointId`. Источник
точки равен `automatic` либо `user`; закрепить (`pinned=true`) можно только
пользовательскую точку. Трасса содержит минимум две точки, не содержит
нулевых сегментов и состоит только из горизонтальных и вертикальных отрезков.
Версия алгоритма позволяет в будущем менять автоматический маршрутизатор, не
меняя смысл уже сохранённой геометрии.

Старое поле `GraphicalRepresentation.route_points` сохранено только как
контейнер совместимости. Новые соединения используют `DiagramRoute`. Если
миграция не может доказать смысл старой линии, геометрия остаётся в
`route_points`, а объект получает явный признак проверки вместо догадки.

Подробный контракт приведён в [diagram-routes.md](diagram-routes.md).

## Каталоги и снимки

`catalogs` содержит строгий пользовательский каталог с постоянным `CatalogId`.
`catalog_snapshots` хранит точные снимки реально использованных записей,
версию исходной записи, источник и переопределения экземпляра. Изменение общего
каталога после сохранения проекта не меняет его снимок.

## Постоянные ID и ссылки

При сохранении и загрузке проверяется межслойная уникальность собственных ID:
оборудования, портов, узлов, подключений, логических линий, конструктивных
участков, страниц, представлений, трасс, точек маршрута и каталогов. Общий
`FeederId` является идентификатором одного фидера, поэтому повторное членство
нескольких линий в том же фидере не считается новым владельцем ID.

Копирование создаёт новые ID трасс и точек маршрута. Ссылки на представления,
порты, узлы и оборудование должны быть переадресованы только на действительно
скопированные сущности. Удаление представления с зависимой трассой либо
запрещается, либо выполняется явным каскадом.

JSON проверяется на любой глубине. `NaN`, `Infinity`, циклические значения и
неподдерживаемые типы не записываются.

## Миграции v1–v7

Миграции выполняются последовательно над копией исходного JSON. Повторная
обработка одного и того же старого файла создаёт те же детерминированные ID,
если состав исходных ID не менялся. Поля будущей версии в старом формате
отвергаются, а не молча принимаются.

### Миграция v5→v6

Миграция создаёт конструктивные участки, пустую графическую модель, проектные
снимки каталога и журнал. Новые ID выбираются детерминированно и без коллизий.

### Миграция v6→v7

Миграция:

1. добавляет `feeder_id=null` существующим логическим линиям;
2. помечает сохранённую положительную физическую длину v6 как подтверждённую;
3. помечает сопротивление подтверждённым только при наличии явных эффективных
   `r1_ohm_per_km` и `x1_ohm_per_km` в наследуемых, ветвевых либо сегментных
   данных;
4. переводит diagram v1 в diagram v2;
5. преобразует старую трассу только тогда, когда одновременно доказаны её
   электрический смысл, два конца и строгая ортогональность;
6. сохраняет неоднозначную геометрию без потери и добавляет признак
   `rza_calc.stage4_migration_review` со статусом «Требуется проверка после
   миграции»;
7. добавляет запись 6→7 в `migration_journal`.

Координаты ни на одном шаге не используются для определения длины,
сопротивления или места физического разделения линии.

## Резервная копия, журнал и атомарная запись

Обычное `load_project()` не изменяет исходный файл. Если `save_project()`
перезаписывает путь проекта старой версии, перед записью создаётся соседняя
копия:

```text
<имя>.before-v7.from-v<версия>.<UTC>.<token>.backup
```

Сведения о преобразовании и имени резервной копии добавляются в
`migration_journal`.
Новый JSON полностью формируется и проверяется до создания резервной копии, а
затем записывается во временный файл и атомарно заменяет целевой файл через
`os.replace`. `migrate_project_file()` выполняет тот же безопасный сценарий на
месте. `restore_project_backup()` сначала проверяет резервную копию и сохраняет копию
заменяемого файла.

`ProjectData.source_format_version` хранит версию реально прочитанного файла.
После успешного сохранения она становится равна 7.

## Редактируемость и готовность к расчёту

Целостный проект разрешено сохранить, даже если подтверждение физических
данных ещё не завершено. Такие состояния представлены типизированными
диагностиками, например `line_data_unconfirmed`. Они не ослабляют проверку
ссылок, ID или электрической топологии.

Перед расчётом вызывается `ProjectData.require_calculation_ready()`. При любом
блокере расчёт запрещён. Совместимый `ProjectData.network` в таком проекте
может содержать только безопасное нерасчётное представление для старой
навигации; использовать его для вычислений нельзя. Тем самым подключённая
неподтверждённая линия не удаляется из канонической модели и не попадает в
расчёт как достоверная.

## Интерфейсы

- `load_project()` и `save_project()` — канонические интерфейсы v7;
- `migrate_project_file()` — миграция файла на месте с резервной копией;
- `restore_project_backup()` — проверенное восстановление;
- `save(path, core.Network)` — только совместимый старый модуль записи v2; он не может
  честно восстановить порты, узлы, линии и трассы и поэтому не пишет v7;
- `load(path)` — совместимое чтение производного `core.Network`; новый код
  использует `ProjectData.electrical_model` и `ProjectData.diagram`.
