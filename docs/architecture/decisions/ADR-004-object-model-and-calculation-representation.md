# ADR-004: объектная модель и расчётное представление

- Статус: принято на Этапе 2.5
- Дата: 2026-08-25

## Контекст

Пользователь работает с оборудованием, а расчётному ядру нужны узлы, ветви и
служебные объекты. Если разрешить независимо редактировать обе модели, они
неизбежно расходятся. Размещение этой логики в интерфейсе связывает электрическую
семантику с конкретным редактором.

## Решение

`ElectricalModel` является единственным каноническим источником оборудования,
портов, узлов, connections, параметров и режимов.

Топологическое и расчётное представления строятся односторонними builders:

```text
ElectricalModel + OperatingState
        ├──> неизменяемый TopologySnapshot
        └──> неизменяемая CalculationProjection
```

Правила преобразования принадлежат отдельному прикладному/доменному слою и не
импортируют компоненты интерфейса. Каждый производный объект трассируется к
исходным постоянным ID.

## Редактирование параметров

Пользователь не изменяет автоматически созданную ветвь напрямую. Ручное
расчётное изменение оформляется как доменное переопределение с исходным и новым
значениями, причиной, источником, датой и признаком ручного ввода. После этого
проекция строится заново.

## Последствия

- Нет обратной синхронизации из расчётного слоя в доменный.
- Интерфейс, отчёт и диагностика читают одну и ту же проекцию.
- Внутренние узлы, например звезда 3W, не обязаны иметь изображение.
- Изменение revision инвалидирует производные снимки.
- Ошибка преобразования блокирует расчёт и содержит ID исходного объекта.
- Этап 2.5 не реализует ТКЗ: решение определяет границу данных, а не формулы.
