# ADR-009: расчётный граф как производное представление

- Статус: принято на Этапе 2.5
- Дата: 2026-08-25

## Контекст

Топологическая проводимость и расчётная схема замещения отвечают на разные
вопросы. Одна топологическая гиперсвязь 3W удобна для связности, но расчёту нужны три
ветви и внутренний узел. Использование совместимого `core.Network` как источника
истины также возвращает синтетические служебные объекты в редактируемую модель.

## Решение

Отдельный построитель автоматически создаёт неизменяемый расчётный граф из
проверенного `ElectricalModel` и совместимого `TopologySnapshot`.

Типовые правила:

- линия — одна ветвь с упорядоченными конструктивными участками и явно
  заданными параметрами последовательностей;
- трансформатор 2W — одна ветвь с коэффициентом трансформации;
- трансформатор 3W — три ветви и внутренний узел звезды;
- генератор — ветвь к внутренней ЭДС;
- нагрузка/шунт — специализированная ветвь к опорному узлу;
- реклоузер — управляемая ветвь текущего режима.

ID служебных узлов и ветвей детерминированы. Trace отображает каждый расчётный
объект на исходные equipment/port/node ID. Проекция не сериализуется как вторая
каноническая сеть и не редактируется независимо.

## Последствия

- `TopologySnapshot` остаётся источником активной связности, а расчётный граф
  — источником входных DTO расчётного ядра.
- Служебная звезда 3W не создаёт ложного электрического узла на схеме.
- Изменение Domain Model или режима требует новой проекции.
- Неизвестный behavior либо неполная схема дают блокирующую диагностику.
- Диагностическая таблица может показывать производные ветви read-only.
- Legacy `adapt_to_calculation()` на Этапе 2.5 остаётся отдельным совместимым
  доступным только для чтения представлением существующего ядра. У него нет обратной синхронизации, и он не
  заменяет каноническую `CalculationProjection`.
- ADR не утверждает, что расчёт ТКЗ уже реализован.
