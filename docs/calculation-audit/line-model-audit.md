# Аудит расчётной модели линий

Дата проверки: **27.08.2026**.

## Канонический путь

Логическая линия, электрическая ветвь, конструктивные участки и графические
сегменты разделены. Для новой `line_section` адаптер:

1. читает физическую длину конструктивных участков в миллиметрах;
2. переводит её в километры;
3. требует подтверждённые `r1_ohm_per_km/x1_ohm_per_km`;
4. суммирует `r·L/n` и `x·L/n` в порядке участков;
5. передаёт старому DTO точный последовательный эквивалент;
6. блокирует расчёт составной ветви, если хотя бы один участок не подтверждён.

Эта часть соответствует требованию не подменять отсутствующие параметры.
Параметры `R2/X2/R0/X0` сохраняются в канонической модели, но существующий
решатель их не использует.

## Матрица видов и уровней модели линии

| Объект требования | Представление в коде | Участие в электрическом графе и ТКЗ | Проверка и граница |
|---|---|---|---|

| КЛ | `LineKind.CABLE`, тип `builtin.line_section.cable` | Тот же двухполюсный расчётный путь по подтверждённым R1/X1 | Структура и адаптация проверены; ёмкость и частота в ТКЗ не участвуют, `ic_per_km` используется только смежным расчётом ОЗЗ |
| Шинопровод | `LineKind.BUSDUCT`, тип `builtin.line_section.busduct` | При явно заданных R1/X1 адаптер передаёт точный последовательный эквивалент через ограниченный legacy-тип линии; без явного импеданса расчёт блокируется | `test_busduct_without_explicit_impedance_blocks_legacy_calculation`; собственного типа `LineBranch.line_type=busduct` в legacy-core нет, поэтому полная модель шинопровода отсутствует |

| Логическая линия | `LogicalLine` и упорядоченный `section_equipment_ids` | Сама не проводит ток и не становится расчётной ветвью; это пользовательская группировка | Инварианты порядка и принадлежности проверяются Domain Model; нельзя трактовать как один неразделённый Z |
| Электрическая ветвь линии | Двухпортовое оборудование `LineSection` между соседними `ElectricalNode` | Создаёт одну `CalculationBranchKind.LINE`, если внутри нет отдельного электрического узла | Проекция проверена; после отпайки одна логическая линия состоит из нескольких таких ветвей |

| Отпайка | Общий `ElectricalNode` и отдельные соседние `LineSection` | Предыдущий, следующий и боковые участки являются обычными ветвями одного графа | Полная сценарная матрица приведена в `topology-calculation-audit.md`; пример 4 аудита проверяет только последовательную магистраль, а не боковую ветвь |

## Матрица параметров конструктивного участка

| Параметр §14 | Где хранится | Фактическая единица / преобразование | Использование текущим ТКЗ | Поведение при отсутствии |
|---|---|---|---|---|
| Физическая длина | `LineConstructionSegment.length_mm` | мм; адаптер переводит в км делением на `1 000 000` | Умножает удельные R1/X1 | Неизвестная или неподтверждённая длина native-участка ставит blocker; legacy `length_km≤0` блокирует `Network.validate()` |
| R1 | `properties.r1_ohm_per_km` | Ом/км; для сегмента вычисляется `r1·L/n` | Используется как действительная часть положительной последовательности | В native-пути отсутствие/неподтверждённость блокирует; прямой legacy API может подставить `ρ/S` |
| X1 | `properties.x1_ohm_per_km` | Ом/км; для сегмента вычисляется `x1·L/n` | Используется как мнимая часть положительной последовательности | В native-пути отсутствие/неподтверждённость блокирует; прямой legacy API может взять ориентировочный X КЛ/ВЛ |
| R2 / X2 | `properties.r2_ohm_per_km`, `x2_ohm_per_km` | Ом/км | Сохраняются и попадают в общую проекцию, но legacy-адаптер и решатель ТКЗ их не используют | Отсутствие не блокирует Iк3; полноценный Iк2 не строится |
| R0 / X0 | `properties.r0_ohm_per_km`, `x0_ohm_per_km` | Ом/км | Сохраняются, но текущий трёхфазный Ybus их не использует; исторические поля `LineBranch.r0/x0` фактически получают R1/X1 | Отсутствие не блокирует Iк3; однофазное КЗ не реализовано |
| Погонное или полное значение | Канонические поля — погонные; адаптер создаёт полный эквивалент | Суммируются полные Ом по сегментам; затем служебно нормируются на общую длину для legacy DTO, чтобы повторное `r·L` вернуло ту же сумму | В Ybus поступает полное комплексное сопротивление ветви | Отдельного типизированного поля «это полное значение» нет; семантика задана именами полей и кодом |
| Количество параллельных проводников/цепей | `properties.parallel_count`, по умолчанию `1` | Безразмерное целое; R и X каждого сегмента делятся на значение | Используется | Неверное значение блокируется адаптером/legacy-валидацией; физическая взаимная связь параллелей не моделируется |
| Число кабелей в пучке | Отдельного типизированного поля нет | — | Не используется | Если записать в `custom_parameters`, решатель его не читает и отдельного предупреждения не выдаёт |
| Коэффициенты условий прокладки | Отдельных типизированных полей нет | — | Не используются в ТКЗ | Не блокируют расчёт; могут существовать только как пользовательские данные без расчётного смысла |
| Источник параметров | Источник каталожного снимка хранится на уровне записи/привязки оборудования; отдельного источника у каждого конструктивного сегмента нет | Текст/ID метаданных, не физическая величина | В формуле не участвует | Отсутствие источника не блокирует расчёт; provenance сегмента неполон |
| Подтверждённость | `length_confirmation`, `impedance_confirmation` | `confirmed` / `unconfirmed` | Управляет допуском native-ветви в legacy-расчёт | Неподтверждённая длина или R1/X1 блокирует; подтверждённость R2/R0 отдельно не представлена |

Поля «число кабелей в пучке», «условия прокладки» и источник каждого
конструктивного сегмента не следует считать реализованными только потому, что
существует свободный объект `custom_parameters`: адаптер ТКЗ эти данные не
интерпретирует.

## Старый DTO и фактическая формула

`LineBranch.r0/x0` исторически называются как параметры нулевой
последовательности, но фактически получают канонические `r1/x1`. Формула:

`R=r0·L·kt/n`, `X=x0·L/n`.

Если DTO создаётся напрямую и `r0/x0` не заданы, код способен взять:

- удельное активное сопротивление из `ρ/S`;
- ближайшее табличное X кабеля;
- типовое `0,40 Ом/км` для ВЛ.

Файл `data/cables.json` помечает эти данные как `ОРИЕНТИРОВОЧНЫЕ`,
`verified=false`. В новом подтверждённом пути адаптер ставит blocker, но
legacy API всё ещё способен рассчитать обычное число по ориентировочным данным.

## Контрольные результаты

- Пример 1, один участок `0,1+j0,4 Ом`: **совпал**.
- Пример 2, две независимые параллельные ветви: общий ток и половинные токи
  ветвей **совпали**.
- Пример 4, три последовательных участка `0,05+j0,2 Ом`: токи после первого,
  второго и третьего участка **совпали**.
- Пример 6: физические сопротивления ВЛ-110 и КЛ-10 суммируются правильно в
  омах, но неверно переводятся в общую систему из-за `Uср=115/10,5 кВ` вместо
  заданных баз 110/10 кВ. Это часть `AUD-SC-001`.
- Разбиение конструктивного участка по физической длине сохраняет сумму длин и
  сумму подтверждённого R1 в `test_21_split_preserves_total_physical_length`
  и `test_22_split_preserves_confirmed_impedance_sum`. Длина графического
  маршрута в этих операциях не используется.

## Риски

- Физический смысл `r0/x0` неоднозначен и опасен при развитии несимметричных КЗ.
- `kt=1,2` берётся из профиля-заглушки и не связан с температурой конкретного
  проводника.
- Погонные поперечные проводимости, ёмкость и параметры нулевой/обратной
  последовательностей решателем не используются.
- Отрицательные R/X и конечность чисел не проверяются самим `core.Network`.

## Дефект `AUD-LINE-001` — высокая критичность

`core.Network.validate()` не проверяет знак явно заданных `r0/x0`
(исторические имена прямой последовательности). Воспроизведена линия с
`r0=-0,1 Ом/км`: валидация не выдаёт ошибки, и непассивная ветвь попадает в
Ybus как обычная. Канонический адаптер проверяет конечность числа, но также не
задаёт физическую границу знака. На этапе 4.6 нужно разделить допустимые
отрицательные параметры специальных эквивалентов и обязательную
положительность обычной ВЛ/КЛ.

Исполняемая карточка: `tests/calculation_audit/test_input_integrity.py::`
`test_negative_line_impedance_must_be_rejected` (`strict xfail`).
