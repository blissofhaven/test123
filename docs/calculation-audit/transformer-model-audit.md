# Аудит модели трансформаторов

Дата проверки: **27.08.2026**.

## Двухобмоточный трансформатор

Фактически используются `Sном[кВА]`, `UВН[кВ]`, `Uk[%]` и необязательное
`Pк[кВт]`. Production сначала получает Z и R на стороне ВН, вычисляет X, затем
приводит комплексное сопротивление к общей ступени.

Контрольный пример 3 (1 МВА, 10/0,4 кВ, Uk=6 %, R=0) дал
`24,056261216234407 кА` при ожидаемых `24,0562612162 кА`: аналитический пример
пройден в строгом допуске.

## Матрица типов трансформаторов

| Тип §15 | Представление | Расчётное разложение | Статус проверки и ограничение |
|---|---|---|---|
| Двухобмоточный | `builtin.transformer_2w` → одна `CalculationBranchKind.TRANSFORMER` → legacy `TransformerBranch` | Одна последовательная ветвь R+jX между узлами ВН и НН | Частный расчёт Z и тока проверен примером 3; паспортный коэффициент трансформации, группа и нейтраль в Ybus не проверены |
| Трёхобмоточный | `builtin.transformer_3w`; legacy `Transformer3W` | Три ветви `TRANSFORMER_WINDING` и один детерминированный внутренний узел `TRANSFORMER_STAR`; legacy-core также создаёт служебный узел `__star` | Структура проверена `test_transformer_3w_projects_to_three_branches_and_one_internal_star` и `test_transformer_3w_has_star_connectivity_without_a_false_ring`; алгебра Uk проверена, независимый нормативный токовый пример отсутствует |
| С расщеплённой обмоткой | Отдельного builtin-типа, набора портов и projection-handler нет | Не формируется | **Отсутствует**; произвольное пользовательское свойство не создаёт ветви расщепления |
| Автотрансформатор | Слово `autotransformer` есть только в старой физической классификации `domain/model.py`; в каноническом реестре электрического оборудования и projection registry обработчика нет | Не формируется как самостоятельная электрическая модель | **Не реализован в текущем расчётном пути**; расчёт как обычного 2W был бы неподтверждённой подменой |
| Внутренние узлы сложного оборудования | `internal_calculation_node_id(equipment_id, "star")` для 3W | Служебный узел не является отдельным пользовательским объектом и имеет стабильный детерминированный ID | Реализовано для 3W; для split/autotransformer специальных внутренних узлов нет |

Два параллельных трансформатора в legacy-core проверяются существующим
`tests/test_core.py::test_sc_parallel_transformers_via_tie`. Этот тест
подтверждает учёт двух ветвей графом, но не расширяет область подтверждения
паспортной формулы или коэффициента трансформации.

## Матрица паспортных и расчётных параметров 2W

| Параметр §15 | Хранение / фактическое использование | Статус |
|---|---|---|
| `Sном` | `TransformerBranch.s_nom`, кВА; входит в Z, R и запасной номинальный ток | Используется; неположительное значение блокируется |
| `UВН` | `TransformerBranch.u_hv`, кВ; через `Methodology.u_avg()` задаёт сторону вычисления Z | Используется, но смешано с табличным `Uср`; положительность проверяется |
| `UНН` | `TransformerBranch.u_lv`, кВ | Хранится и проверяется только на положительность; в `transformer_impedance()` и `ShortCircuitSolver` не используется |
| `Uk%` | `TransformerBranch.uk`, % | Используется в `Z=10·Uk·Uср²/Sном`; для обычного 2W отрицательный знак ошибочно разрешён (`AUD-TR-001`) |
| `Pк` | `TransformerBranch.p_k`, кВт | Необязательно используется для R; при отсутствии R=0 и расчёт продолжается с пояснением |
| `Pхх` | Типизированного поля в `TransformerBranch` и обязательной карте адаптера нет | **Отсутствует и не используется** |
| `Iхх` | Типизированного поля в `TransformerBranch` и обязательной карте адаптера нет | **Отсутствует и не используется** |
| Коэффициент трансформации | `CalculationBranch.nominal_ratio` выводится из классов напряжения портовых групп ВН/НН | Присутствует в производной проекции, но legacy-решатель Z/Ybus его не применяет как паспортное отношение; приведение выполняется через таблицу `Uср` |
| РПН / ПБВ | Типизированной позиции и диапазона нет | **Отсутствует** |
| Группа соединения | `TransformerBranch.group` | Хранится в legacy DTO, но на фазу, последовательности и ток не влияет |
| Заземление нейтрали | Общая карта `Network.neutral` относится к ступени напряжения, не к конкретной обмотке | В текущем Iк3 не используется; модель нейтрали обмотки отсутствует |
| Сопротивление нейтрали | Отдельного поля обмотки нет | **Отсутствует** |
| Сторона приведения | Z сначала вычисляется на `u_hv`, затем `refer_z()` переводит его на общую `u_base` через отношения `Uср` | Реализовано, но несогласованность классов, паспортных отношений и баз пример 6 выявила как `AUD-SC-001` |
| Параметры в о.е. | В production 2W отдельные `r_pu/x_pu/z_pu` не хранятся и не являются входным интерфейсом | **Отсутствуют**; о.е. использованы только независимым примером аудита |
| Параметры в омах | R+jX создаётся `transformer_impedance()` | Реализовано для положительной последовательности с указанными ограничениями |

## Что не участвует в результате

- `TransformerBranch.u_lv` не читается ни `transformer_impedance()`, ни
  `ShortCircuitSolver`. При неизменных узлах значения 0,4; 0,69 и 6,3 кВ дали
  один и тот же ток.
- `group` хранится, но не используется.
- Положение РПН/ПБВ, фактический коэффициент трансформации, угол сдвига,
  состояние нейтрали и сопротивление нейтрали отсутствуют в расчёте.
- `z_loop` существует только как отдельное legacy-поле для будущего/другого
  расчёта и не входит в текущий трёхфазный Ybus.
- `Pхх` и `Iхх` не представлены типизированными полями рабочего
  `TransformerBranch`; их возможное наличие среди произвольных свойств Domain
  не делает их расчётными параметрами.

Следовательно, пример 3 подтверждает только частный радиальный случай с
согласованными классами узлов. Он не подтверждает работу трансформатора в
замкнутой многoисточниковой сети и при отличающемся коэффициенте трансформации.

## Трёхобмоточный трансформатор

Физический объект разворачивается в служебную звезду из трёх ветвей. Лучевые
`Uk` получаются половинными комбинациями попарных `Uk`; отрицательный средний
луч допускается. Это сохраняет попарные реактивные суммы.

Ограничения:

- все лучи рассчитываются на `u_hv`;
- единственное `p_k` назначается только головному лучу, у остальных R=0;
- нет отдельных потерь КЗ по парам обмоток;
- нет проверки физической реализуемости набора попарных данных, кроме ошибок
  непосредственно в `sqrt`;
- группа и нейтрали не влияют на расчёт.
- отдельные паспортные напряжения, мощности и потери каждой обмотки не
  моделируются; внутренний узел звезды является служебным расчётным узлом, а
  не подтверждением полноты эквивалентной схемы.

**Источник и корректность полной модели трёхобмоточного трансформатора не
подтверждены.** Существующий тест проверяет алгебраические суммы `Uk`, но не
сверяет токи трёхобмоточного аппарата с независимым нормативным примером.

## Дефект `AUD-TR-001` — высокая критичность

Отрицательный луч звезды действительно может возникать при корректном
преобразовании попарных `Uk` трёхобмоточного трансформатора. Однако
`core.Network.validate()` не отделяет этот служебный случай от обычного
двухобмоточного `TransformerBranch`: отдельный аппарат 2W с `Uk=-6 %` проходит
валидацию и участвует в Ybus с отрицательным реактивным сопротивлением. В
последовательной схеме это может частично компенсировать реальное X сети и
опасно завысить ток.

Исполняемая карточка: `tests/calculation_audit/test_input_integrity.py::`
`test_negative_two_winding_transformer_uk_must_be_rejected` (`strict xfail`).
