# Рекомендуемая архитектура будущего расчётного ядра

Статус документа: **рекомендация этапа 4.4, не реализация**.

Предложения ниже должны обсуждаться на архитектурном этапе 4.5. Производственный
алгоритм в рамках 4.4 не менялся.

## Цели

Будущее ядро должно:

* получать электрическую схему только из канонической Domain Model;
* отделять исходное оборудование от производного расчётного представления;
* рассчитывать полноценный граф, а не один найденный путь;
* явно разделять прямую, обратную и нулевую последовательности;
* возвращать комплексные напряжения и направленные токи ветвей;
* хранить происхождение каждого параметра и результата;
* определять устаревание результата по электрическому fingerprint;
* использовать типизированные физические величины на границах;
* давать диагностируемый, воспроизводимый и масштабируемый численный результат;
* не зависеть от GUI, SVG, координат и legacy `core.Network`.

## Однонаправленный поток зависимостей

```text
ElectricalModel + OperatingState + CalculationSettings
                         │
                         ▼
             ValidatedElectricalSnapshot
                         │
                         ▼
              CalculationProjection
        equipment → internal nodes/branches
                         │
                         ▼
          SequenceNetworkBuilder (1 / 2 / 0)
                         │
                         ▼
            SparseAdmittanceAssembler
                         │
                         ▼
       Factorization / linear solves / diagnostics
                         │
                         ▼
               FaultResultBundle
                         │
                         ▼
        Presentation / report / export adapters
```

Запрещённые обратные зависимости:

```text
Domain Model  ← core.Network
Domain Model  ← GUI/SVG
Kernel        ← GUI widgets
Kernel result ← display rounding
```

Legacy `core.Network` на время миграции следует оставить **выходным DTO
совместимости**, а не источником истины и не типом нового публичного API.

## 1. Неизменяемый расчётный случай

Перед расчётом формируется `CalculationCase`:

```text
CalculationCase
  case_id
  electrical_fingerprint
  electrical_model_revision
  operating_state_id + state_fingerprint
  calculation_settings
  methodology_snapshot + hash
  catalog_snapshot_hashes
  topology_registry_signature
  kernel_version + algorithm_version
  dependency_versions
  created_at
```

Fingerprint должен строиться из **электрически значимых** данных в
каноническом порядке. Координаты, цвет, zoom, точки графического маршрута и
положение подписи в него не входят. Изменение соединения, состояния аппарата,
длины, R/X, трансформатора, источника, методики или override создаёт другой
fingerprint.

Расчёт принимает только неизменяемый snapshot. Мутация рабочей модели во время
решения невозможна; после завершения результат сравнивается с текущим
fingerprint и помечается `актуален` или `устарел`.

Topology cache и Calculation Projection обязаны проверять не только номер
revision, но и fingerprint содержимого плюс `registry_signature`. Это исключает
повторное использование snapshot другой ветви undo/redo-истории или другого
набора behavior handlers.

## 2. Типизированные физические величины

На внешних границах необходимы разные типы, даже если внутри они хранят
`float64`:

* `LineVoltageV` и `PhaseVoltageV`;
* `CurrentA` и `CurrentKa` без неявного взаимозаменяемого API;
* `ApparentPowerVA`, `ActivePowerW`;
* `ResistanceOhm`, `ReactanceOhm`, `ImpedanceOhm`;
* `LengthM` и `LengthKm`;
* `Percent` и `PerUnit`;
* `FrequencyHz`, `TimeS`, `AngleRad`;
* `VoltageClassId`, `RatedVoltage`, `AverageCalculationVoltage`,
  `BaseVoltage`, `PreFaultVoltage` как разные смысловые поля.

Преобразование единиц выполняется в одном слое и отражается в trace. В
матричный слой должны поступать только согласованные SI/именованные единицы и
комплексные величины с документированной ориентацией.

## 3. Производная модель оборудования

Для каждого типа оборудования используется отдельный projection handler:

```text
EquipmentProjectionHandler
  validate(equipment, snapshot)
  emit_nodes()
  emit_branches(sequence)
  emit_sources(sequence)
  trace_parameter_origins()
```

Примеры:

* линия — одна ветвь между соседними электрическими узлами; конструктивные
  участки дают упорядоченную сумму параметров;
* 2W-трансформатор — ветвь с сопротивлением, коэффициентом трансформации и
  моделью нейтрали/группы;
* 3W-трансформатор — один аппарат, внутренний узел звезды и три ветви;
* внешний источник/генератор/двигатель — внутренний источник с явно заданной
  ЭДС и сопротивлениями последовательностей;
* выключатель/разъединитель/реклоузер — управляемая ветвь; открытое состояние
  исключает путь, но не удаляет оборудование;
* нагрузка/шунт — отдельная модель, включаемая только в те постановки, где это
  предусмотрено методикой.

Handler не имеет доступа к виджетам и графическим координатам. Неизвестное или
неполное оборудование формирует блокирующую диагностику; скрытого типового
значения нет.

## 4. Сети последовательностей и виды КЗ

Рекомендуется формировать три отдельные, но связанные сети:

* `PositiveSequenceNetwork`;
* `NegativeSequenceNetwork`;
* `ZeroSequenceNetwork`.

Объединение выполняется отдельным `FaultEquationBuilder` для:

* трёхфазного КЗ;
* двухфазного КЗ;
* однофазного КЗ;
* двухфазного КЗ на землю.

Так коэффициент `0,866` перестаёт быть универсальной заменой сети обратной
последовательности. Группа соединения трансформатора, заземление нейтрали,
сопротивление нейтрали и нулевая последовательность линии начинают участвовать
явно и проверяемо.

Каждый поддерживаемый вид КЗ получает собственный `FaultKind`, набор допущений
и признак металлического/дугового повреждения. Неподдержанный вид возвращает
статус `NOT_SUPPORTED`, а не ноль.

## 5. Матричный слой

Интерфейс матричного слоя не должен зависеть от оборудования:

```text
AdmittanceStamp
  from_node
  to_node
  complex_admittance
  source_branch_id
  orientation
```

Рекомендуемый путь:

1. детерминированно пронумеровать узлы snapshot;
2. объединить только доказанно эквипотенциальные идеальные соединения;
3. собрать разреженную Ybus;
4. проверить связные компоненты и источники до решения;
5. выполнить масштабирование;
6. факторизовать матрицу один раз на топологию/последовательность;
7. решать нужные правые части, не вычисляя полный `inv(Y)` без необходимости;
8. вернуть residual, оценку обусловленности/rcond и диагностические допуски;
9. повторно использовать факторизацию для нескольких точек КЗ, когда входной
   fingerprint не изменился.

Выбор конкретной sparse-библиотеки относится к этапу 4.5. Добавление тяжёлой
зависимости допускается только после benchmark и проверки поставки Windows.
До этого интерфейс должен позволять dense fallback для малых тестов.

## 6. Источники и несколько ЭДС

Источник описывается явно:

```text
SourceModel
  emf_phase_complex
  z1, z2, z0
  parameter_origin
  operating_state
```

Это позволяет учитывать разные модули и углы ЭДС, а также получать вклад
каждого источника. Служебный `GRID` не должен означать, что все независимые
источники имеют одну и ту же идеальную ЭДС без явного допущения.

Результат для каждого источника содержит комплексный ток и ориентацию.
Суммарный ток в точке КЗ проверяется по первому закону Кирхгофа.

## 7. Результат и trace

`FaultResultBundle` должен содержать:

```text
status: OK | INVALID_INPUT | NOT_ENERGIZED | NOT_SUPPORTED | NUMERIC_FAILURE
calculation_case metadata
fault specification
node voltages (complex)
fault current (complex and magnitude)
branch currents (complex, signed, orientation)
source contributions
sequence components
residual / conditioning diagnostics
warnings and blocking errors
parameter provenance
calculation trace
```

Статус острова без источника — `NOT_ENERGIZED` с русским сообщением
«Расчёт невозможен: точка КЗ не связана с активным источником», а не обычный
результат `0 кА`.

Trace строится из фактических stamps и решения. Для кольца нельзя показывать
все ветви как одну последовательную «цепочку сопротивлений». Округление
разрешено только presentation/report-слою; сырые комплексные результаты
сохраняются с полной double precision.

## 8. Кэширование и переключения

Ключ кэша:

```text
(electrical_fingerprint,
 operating_state_fingerprint,
 calculation_settings_hash,
 sequence,
 kernel_algorithm_version)
```

Переключение одного аппарата создаёт новый topology fingerprint. В будущем
можно применять локальное обновление/low-rank factorization, но только после
профилирования и доказательства эквивалентности. На первом шаге важнее
правильное аннулирование результата, чем преждевременная оптимизация.

## 9. Независимая проверка

Тестовый эталонный решатель остаётся в `tests/calculation_audit` и:

* не импортирует production solver;
* самостоятельно собирает малую комплексную Ybus;
* используется только на аналитически проверяемых схемах;
* имеет явные единицы, формулы и допуски;
* сравнивает комплексные значения, а не только модуль;
* не подгоняет результат по имени проекта.

Набор acceptance-примеров должен включать радиальную цепь, две параллельные
ветви, два источника с разных сторон, кольцо, остров, 2W/3W-трансформатор,
смешанную линию, три отпайки и реклоузер.

## 10. Миграционный путь

1. Заморозить текущее legacy-поведение тестами и пометить границы
   достоверности.
2. Ввести `CalculationCase` и fingerprint, не меняя чисел.
3. Ввести типизированные параметры и явные адаптеры единиц.
4. Реализовать новый positive-sequence solver параллельно старому.
5. Сравнивать оба пути на подтверждённых примерах; расхождения объяснять.
6. Добавить сети 2/0 и новые виды КЗ.
7. Перевести native Domain-оборудование на новое ядро.
8. Оставить legacy `core.Network` только для чтения старых проектов на
   ограниченный период.
9. Удалять старый путь только после миграции формата, отчётов и полного
   acceptance-набора.

Такой порядок не требует переписывать редактор и расчёт одновременно и
снижает риск скрытой смены численного поведения.

## Критерии архитектурной готовности

До промышленного включения нового ядра должны быть выполнены одновременно:

* для каждой формулы есть источник и область применимости;
* нет неявного смешения единиц;
* результат привязан к fingerprint и версии алгоритма;
* для каждой ветви доступен комплексный направленный ток;
* несколько источников и кольца проходят независимые тесты;
* остров без источника имеет отдельный статус;
* численная диагностика включает residual и обусловленность;
* 10/100/1000/5000 узлов имеют повторяемый benchmark и бюджет;
* native Domain-проект проходит сохранение, повторное открытие и расчёт без
  обращения к compatibility equipment;
* GUI только отображает результат и не участвует в формулах.
