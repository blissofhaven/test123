# Этап A3 — Модель параметров оборудования

**Трек:** A · **Исполнитель:** Max · **Зависит от:** A1 · **Оценка:** 4–6 дней

## Цель

Сделать параметры оборудования описанными данными, а не кодом. Это фундамент
сразу для трёх вещей: справочников (A4), новых типов оборудования (A5) и
панели свойств (B5). Пока модели нет, каждый новый тип добавляется вручную в
пяти местах, а панель свойств знает про типы больше, чем должна.

## Входной контроль

- A1 закрыт, эталон заморожен, `status.json` показывает `baseline.frozen`;
- `PropertyDefinition` в `domain/electrical.py` существует и используется
  участками линий и реклоузером;
- у остальных типов параметры лежат в legacy-DTO расчётной ветви.

## Граница этапа

**Разрешено:** `rza_calc/domain/**`, `rza_calc/io/**` (сериализация
параметров), `rza_calc/adapters/**` (чтение параметров), тесты, документация.

**Запрещено:** менять физические формулы и расчётные значения. Модель
описывает те же величины, которые уже используются.

**Числа:** не меняются. Тест-снимок обязан остаться зелёным.

## Состав работ

### 1. Три категории полей

| Категория | Поведение при отсутствии | Пример |
|---|---|---|
| **Обязательное** | расчёт блокируется с сообщением, называющим параметр | `Sном`, `Uк`, длина, сечение |
| **Необязательное** | предупреждение с указанием принятого допущения | `ΔPк` (принято R = 0), `X/R` (принято чисто индуктивным) |
| **Пользовательское** | в расчёте не участвует | инвентарный номер, год ввода, примечание |

Правило: если отсутствие параметра меняет результат — параметр либо
обязательный, либо его допущение обязано попасть в предупреждение и в
протокол. Молчаливых допущений быть не должно.

### 2. Типизированные величины

Сейчас почти всё — `float`, и ошибки В/кВ, А/кА, кВА/МВА невозможно отсеять.
Каждому параметру задать:

* единицу измерения (кВ, А, кВ·А, %, Ом/км, км, мм², с);
* допустимый диапазон;
* число значащих цифр для отображения;
* признак «может быть отрицательным» (нужен лучу звезды 3W).

Проверка на границе: недопустимое значение отклоняется с сообщением, где
названы параметр, введённая величина, единица и допустимый диапазон.

### 3. Группы для панели свойств

`Паспорт` · `Электрические` · `Защита` · `Эксплуатация` · `Прочее`.
Порядок групп и порядок полей внутри — часть модели, чтобы панель свойств
строилась данными, а не кодом.

### 4. Происхождение значения

У каждого значения хранить: введено вручную / взято из каталожной записи /
принято по умолчанию. Нужно и в панели свойств, и в протоколе расчёта, и для
этапа A4 — чтобы видеть, что переопределено относительно каталога.

### 5. Описание встроенных типов

Для каждого из 14 существующих типов перечислить обязательные и
необязательные поля с единицами и диапазонами. Это одновременно
документация и проверяемый контракт.

## Что отдать Sol

В отчёте — раздел «Контракт для панели свойств»:

* как получить список групп и полей для типа оборудования;
* как узнать обязательность, единицу, диапазон, происхождение;
* как записать значение и получить ошибку валидации;
* как добавить пользовательское поле;
* пример: полный код построения панели для двухобмоточного трансформатора.

## Критерии готовности

* Панель свойств может быть построена **только** по модели, без знания типов.
* Отсутствие обязательного поля блокирует расчёт с внятным сообщением.
* Отсутствие необязательного даёт предупреждение с названным допущением.
* Пользовательское поле переживает сохранение и открытие проекта.
* Ошибка единиц (например, 10 000 кВ вместо 10 кВ) отклоняется на вводе.
* Тест-снимок расчётных чисел зелёный.
