# Разбор промта «4.6.2 / D2 — разреженный backend»

Дата: 28.08.2026. Проверено на фактическом состоянии
`rza-calc-0.3-safe-hardening`, все цифры ниже измерены, а не оценены.

---

## Вердикт

Промт написан аккуратно — с Gate, границами этапа, запретом скрытого fallback
и требованием сравнения с эталоном. Это хороший документ. Проблема не в
качестве, а в **месте в очереди**: он описывает этап, который нельзя начинать,
и решает задачу, которой у проекта сейчас нет.

Три причины, каждая достаточна сама по себе:

1. **Gate не проходится** — этапа D1 (4.6.1) не существует, как и этапа 4.5-ТКЗ
   перед ним. Промт сам это обнаружит и остановится.
2. **Он оптимизирует 0,16 % времени расчёта.** Плотная инверсия матрицы, ради
   устранения которой затевается весь этап, занимает доли процента; 99 % уходит
   в топологические запросы графа.
3. **Он заморозит как эталон те числа, которые сейчас неверны** — раздел
   «Запрещено менять… пользовательские результаты контрольных примеров»
   превращает завышение тока на 6/10/35 кВ и ложные «✓» в отсечке в
   регрессионный контракт.

## 1. Gate провалится на первом же пункте

Промт требует (§48-58) изучить и проверить:

| Что требует промт | Факт в проекте |
|---|---|

| `docs/calculation/positive-sequence-solver.md` | папки `docs/calculation` нет |
| `docs/calculation/positive-sequence-mathematics.md` | нет |
| `docs/architecture/linear-system-backend.md` | нет |
| `docs/architecture/calculation-pipeline.md` | нет |
| новый решатель на `CalculationProjection` | нет; считает legacy `core.Network` |
| `CalculationService` | не существует |
| SciPy | не в зависимостях |

Более того, в самом проекте написано прямым текстом
(`docs/work-verification/stage-4-5-tkz-report.md:91-99`):

> **Часть Б — этап 4.5-ТКЗ. Статус: не начата.**
> Не создавались единый новый расчётный путь, целевые `CalculationCase`,

То есть до D2 не хватает **двух** этапов, а не одного. По собственным правилам
промта (§92-103) исполнитель обязан создать
`docs/work-verification/stage-4-6-2-blocked.md` и остановиться. Это правильное
поведение промта — но результатом дня работы будет один файл «заблокировано».

## 2. Sparse решает 0,16 % задачи

Главный аргумент. Промт исходит из того, что узкое место — плотная `Ybus` и
`numpy.linalg.inv`. Измерил профилировщиком на реальном проекте
`examples/gtes_sever.json` (71 узел, 103 ветви, 5 режимов):

```
полный run()                                   4,71 с
  Network.adjacency()      11 946 вызовов      3,52 с   (75 %)
  branch_conducting()   1 334 159 вызовов      2,85 с
  switch_ids()            945 691 вызов        1,47 с
построение всех решателей КЗ (5 режимов)       0,0136 с (0,3 %)
один numpy.linalg.inv на матрице 67×67         0,000174 с
```

`Network.adjacency()` каждый раз заново обходит все ветви и строит словарь
смежности — кэша нет. Его дёргают `orient()`, `downstream_nodes()`,
`energized_nodes()`, `upstream_branch()`, `zone_points()`, и каждый из них
вызывается для каждой защиты × каждого режима × каждой точки зоны.

Как это масштабируется (радиальный фидер, 2 режима, защита на каждом участке):

| Ветвей | Матрица (все режимы) | Полный `run()` | Доля матрицы |
|---:|---:|---:|---:|
| 26 | 3,3 мс | 0,09 с | 3,59 % |
| 51 | 4,7 мс | 0,42 с | 1,11 % |
| 101 | 16,2 мс | 2,32 с | 0,70 % |
| 201 | 49,9 мс | 14,38 с | 0,35 % |
| 401 | 157 мс | **96,3 с** | **0,16 %** |

Полное время растёт примерно как **N^2,7**, доля матрицы падает. Схема из
400 участков уже считается полторы минуты — и sparse-backend ускорит из них
0,16 секунды.

**Что это значит для обязательного benchmark 5000 узлов** (§997-1007):
экстраполяция по N^2,7 даёт порядка **суток** на один расчёт. Не из-за
матрицы — из-за графового слоя. Требование «5000 узлов рассчитаны без dense
NxN» формально можно выполнить и всё равно не дождаться результата. Промт
поставил верную цель, но указал не на то место.

**Вывод:** прежде чем менять численный backend, нужно закэшировать
`adjacency()` и производные обходы. Это правка на несколько десятков строк,
которая по измерениям выше даёт кратное ускорение там, где sparse не даст
ничего. И только после неё станет видно, где следующее узкое место — вполне
возможно, что это будет уже матрица, и тогда D2 станет осмысленным.

## 3. Этап заморозит неверные числа

Раздел «Граница этапа» (§168-193) запрещает менять физические формулы, модель
напряжений, правила приведения и **«пользовательские результаты контрольных
примеров»**. Требование правильное для рефакторинга производительности — но
только если текущие числа верны.

По результатам аудита ядра (`AUDIT-KERNEL.md`) они не верны:

* ток КЗ на шинах 6/10/35 кВ завышен на ~9,5 % (смешаны Uср и Uном);
* паспортный коэффициент трансформации не используется вообще;
* чувствительность ТО считается в узле со стороны питания, а не в точке
  установки ТТ — Kч = 7,17 «✓» там, где отсечка физически слепа;
* Kч ТО не учитывает токораспределение — 2,255 «✓» вместо фактических 0,49 «✗».

Тесты №1-6, 32, 33 из §877-908 («Sparse и Dense дают одинаковый результат для
примера 1…6», «Batch из 100 точек совпадает с 100 одиночными») закрепят эти
значения как регрессионный контракт. После D2 их исправление будет означать
«поломку» полусотни тестов и пересмотр benchmark-отчётов — то есть станет
дороже, чем сейчас.

Правильный порядок: сначала зафиксировать **верные** контрольные числа, потом
вокруг них строить производительность.

## 4. У главного результата этапа нет потребителя

Основная ценность D2 — пакетный расчёт множества точек КЗ на одной
факторизации (§539: «Пакет из 100 точек КЗ не должен факторизовать одну и ту же
матрицу 100 раз»).

Но точек КЗ как пользовательской сущности в программе нет.
`calculation/fault_location.py` описывает `LineFaultLocation` с точностью до
миллиметра — и во всём `rza_calc/` импортируется только в
`calculation/__init__.py`. Ни решатель, ни редактор, ни адаптер его не читают.
Поставить точку КЗ на линии нельзя.

Сейчас расчёт делает 1 точку на защиту, автоматически. Строить инфраструктуру
на 1000 точек, пока нельзя поставить ни одной вручную, — это оптимизация
несуществующего сценария.

## 5. Ещё несколько частностей

* **§231-257, SciPy.** Зависимость правильная, но тяжёлая для Windows-сборки
  (~90 МБ), и вводится ради того самого 0,16 %. Отложить до момента, когда
  матрица действительно станет узким местом.
* **§705-706 «пороги не подбираются после получения результата»** — хорошее
  правило, стоит сохранить в любом будущем промте.
* **§1113-1117, запрет скрытого fallback sparse → dense → legacy** — правильно
  и важно; сохранить.
* **§378 «изменение состояния инвалидирует matrix fingerprint»** и всё
  разделение `case / matrix / rhs fingerprint` (§418-459) — это хорошая
  архитектурная идея, применимая уже сейчас, независимо от sparse.
  У проекта одна общая проверка fingerprint, и она стоит 13,2 мс на **каждое**
  чтение `project.network` (§4.9 аудита) — разделение fingerprint решило бы
  и эту проблему.
* **§1155-1213: 15 документов и 9 ADR** на этап, у которого не выполнен вход.
  Объём документации превышает объём кода, который она описывает.

## 6. Что делать вместо этого

Порядок, в котором каждый шаг делает следующий дешевле.

**Шаг 1. Исправить ложные «✓» в отсечке.** `core/protections/to.py`, точки
4.3-4.5 аудита. Локально, один файл, убирает самый опасный класс ошибок:
неверное число заметно, а ложное «всё хорошо» — нет.

**Шаг 2. Единый базис напряжений.** Точка 4.1 аудита. Снимает систематические
+9,5 % на 6/10/35 кВ. После шагов 1-2 контрольные примеры можно пересчитать и
**зафиксировать как эталон** — дальше их менять уже нельзя.

**Шаг 3. Кэш топологии.** `adjacency()`, `active_branches()`,
`energized_nodes()`, `orient()`, `downstream_nodes()` — мемоизация по
`(mode_id, network_fingerprint)`. По измерениям §2 это 75 % времени расчёта.
Плюс кэш `electrical_model_fingerprint` в `io/project.py` (13,2 мс на каждое
обращение к `project.network`).
Здесь же полезно взять из промта D2 идею разделения
`case / matrix / rhs fingerprint` — она пригодится и без sparse.

**Шаг 4. Повторить benchmark.** 100 / 400 / 1000 ветвей. Именно здесь станет
видно, нужен ли sparse вообще и при каком размере. Решение о SciPy принимать
по этим числам, а не заранее.

**Шаг 5. Точки КЗ как функция продукта.** Оживить `LineFaultLocation`: разбиение
ветви для расчётной точки, отображение в редакторе, результат по точке. После
этого у пакетного расчёта появится потребитель.

**Шаг 6. Единый расчётный путь (4.5-ТКЗ и D1).** `CalculationCase` →
`CalculationProjection` → решатель, вместо legacy `core.Network`. Только после
этого Gate промта D2 станет проходимым.

**Шаг 7. D2 в исходном виде.** К этому моменту он будет опираться на верные
числа, на измеренную потребность и на существующий сценарий использования.

Шаги 1-4 — это дни, а не недели, и они дают измеримый результат сразу.

## 7. Что из промта D2 сохранить дословно

Документ не выбрасывать. В нём есть части, которые пригодятся в любом порядке
этапов:

* обязательный входной Gate с проверкой фактического кода, а не отчёта;
* явная граница этапа и список запрещённых изменений;
* контрольная точка с ZIP, SHA-256 и манифестом до правок;
* разделение `case / matrix / rhs fingerprint`;
* запрет скрытого fallback между backend;
* требование версионировать и документировать численные пороги *до* измерений;
* сравнение «production vs независимый reference solver» на каждом примере;
* детерминированные случайные сети с фиксированными seed;
* требование не показывать устаревший результат как актуальный.

Это сильные инженерные требования. Вопрос только в том, к какому этапу их
применять.
